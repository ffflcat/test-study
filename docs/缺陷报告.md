
# 缺陷报告 1

| 字段 | 内容 |
|---|---|
| **缺陷编号** | BUG-CS-PRICE-001 |
| **缺陷标题** | 满减阈值边界错误：订单金额恰好 100.00 元时未减 10 元 |
| **发现日期** | 2026-10-22 |
| **报告人** | 测试（待署名） |
| **项目 / 版本** | CampusShop C# 版 / main 分支 @ 648dd89 |
| **所属模块** | `CampusShop.PriceCalculator.ApplyDiscount`（经 `Pricing.TotalFor` 被网页与 API 调用） |
| **缺陷类型** | 功能缺陷 / 边界值处理 |
| **严重程度** | 中（Major）——仅影响恰好 100.00 的边界点，但直接导致用户多付 10 元 |
| **优先级** | 高（P1）——需求条款明确，修复成本低，属金额准确性问题 |
| **可复现性** | 必现（确定性） |
| **发现阶段** | 单元测试 |
| **状态** | 新建 |

## 前置条件

- .NET 10 SDK 环境，测试项目已引用 `CampusShop`。
- 无需登录，无需外部数据。

## 复现步骤

1. 创建 `PriceCalculator` 实例。
2. 调用 `ApplyDiscount(100.00m)`。
3. 读取返回值。

## 预期结果

返回 **90.00**。

计算过程：`100.00 ≥ 100`，满足满减条件，`100.00 − 10.00 = 90.00`。

## 实际结果

返回 **100.00**，未执行满减。

## 需求依据

- **需求 2.1**：订单金额满 100 元（金额 **≥ 100**）时减 10 元。
- **需求 2.2**：不满 100 元不减（本用例不适用）。
- **需求 1.4**：金额计算必须精确，不允许出现浮点误差；`100.00` 是精确边界值。

## 测试证据

- 测试用例：`PriceCalculatorTests.ApplyDiscount_GivenTotal_ReturnsRequirementAmount(total: 100.00, expected: 90.00)`
- 实际输出：

```text
Assert.Equal() Failure: Values differ
Expected: 90.00
Actual:   100.00
```

- 结果：失败。

## 影响范围

1. **网页购物车结算**：当购物车原价合计恰好 100.00 元时，页面“应付金额”显示 100.00，用户多付 10.00 元。
2. **API 直接下单**：商品 p1（笔记本，50.00 元）数量为 2 时，小计 100.00 元，订单金额按 100.00 元记录，未享受满减。
3. **边界对比**：99.99 元不减、100.01 元减 10，行为正确；问题仅出现在恰好 100.00 元这一阈值点。

## 缺陷位置（供定位）

`csharp/src/CampusShop/PriceCalculator.cs:13`

## 建议（不含代码）

按需求 2.1 将“满 100”的判定改为包含 100.00，并保留该边界用例作为回归测试。

## 备注

该用例的期望值取自需求文档，而非当前实现结果。

| **缺陷标题** | `POST /api/orders` 未拒绝负数购买数量，生成负数金额订单并反向增加库存 |
| **发现日期** | 2026-10-22 |
| **报告人** | 测试（待署名） |
| **项目 / 版本** | CampusShop C# 版 / main 分支 @ 648dd89 |

| **缺陷类型** | 输入校验缺陷 / 数据完整性 |
| **严重程度** | 高（Critical）——可被普通登录用户通过 API 触发，影响订单金额与库存数据 |
| **优先级** | 高（P0/P1）——涉及资金与库存，且同项目购物车接口已正确校验，属明显遗漏 |
| **可复现性** | 必现（确定性） |
| **发现阶段** | 接口测试（选项 B：API 层非法输入校验） |

## 前置条件

- 网站以 Development 环境启动（数据保存在内存中）。
- 演示账号 `alice / 123456` 可用。
- 商品 `p1`（笔记本，单价 50.00 元，初始库存 100）存在。
- 已通过 `POST /api/auth/login` 获取 Token。

## 复现步骤

1. 启动网站。
2. 调用 `POST /api/auth/login`，请求体：

```json
{"username":"alice","password":"123456"}
```

取得返回的 `token`。

3. 调用 `POST /api/orders`，请求头 `Authorization: Bearer <token>`，请求体：

```json
{"productId":"p1","quantity":-1}
```

4. 观察 HTTP 状态码与响应。
5. 可选：调用 `GET /api/orders` 查看新订单，调用 `GET /api/products` 查看 `p1` 库存。

## 预期结果

- HTTP **400 Bad Request**，返回参数错误（数量必须在 1 到 99 之间）。
- 不创建订单、不扣款、不改变库存。

## 实际结果

- HTTP **201 Created**，订单创建成功（已由测试实际观测）。
- 按同一请求路径的代码逻辑推导：
  - 订单金额 = `50.00 × (−1) = −50.00`；
  - 库存 `p1` 由 100 变为 101（扣减 −1 等价于增加 1）；
  - 支付金额 −50.00 未超过 5000 元，模拟支付判定为成功；
  - 占用一个新的订单号（首次运行为 1003），并发送“下单成功”通知。

## 需求依据

- **需求 4.6（直接违反）**：购买数量必须是 **1～99 的整数**，否则拒绝下单（API 返回 400）。
- **需求 4.1**：检查库存；不足则返回“库存不足”，不得扣款。负数数量绕过了库存不足判断（`100 < −1` 为假）。
- **需求 4.8**：模拟支付：单笔金额超过 5000 元时支付失败。负数金额不触发该限制，支付被判成功。
- **需求 4.5**：返回“下单成功”及订单号。实际返回成功，但订单金额本身非法。

## 测试证据

- 测试用例：`ShopApiValidationTests.Post_QuantityOutside1To99_Returns400(path: "/api/orders", quantity: -1)`
- 实际输出：

```text
Assert.Equal() Failure: Values differ
Expected: BadRequest
Actual:   Created
```

- 结果：失败。

## 影响范围

1. 登录用户可通过 API 提交负数数量，生成负数金额订单。
2. 库存被反向增加，破坏库存数据的正确性。
3. 负数金额被支付网关视为成功，可能导致账务异常。
4. 同类接口 `POST /api/cart/items` 已正确拒绝负数（返回 400），问题仅存在于 `POST /api/orders`。

## 缺陷位置（供定位）

`csharp/src/CampusShop.Web/ShopApi.cs:76`（数量校验条件仅拒绝 0 和大于 99）

## 建议（不含代码）

按需求 4.6 将校验范围统一为 1～99，负数、0、超过 99 均返回 400，并与购物车接口的校验行为保持一致。

## 备注

- 该缺陷由选项 B 的 API 层非法输入用例发现。
- 该用例会实际创建负数订单并修改内存库存；复现前可通过重启网站或调用开发环境的重置接口恢复初始数据。
- `POST /api/cart/items` 对 0、−1、100 均正确返回 400，可作为对照。

| **缺陷类型** | 功能缺陷 / 日期边界处理 |
| **严重程度** | 中（Major）——仅影响截止日当天，但会让所有符合条件的优惠券在该日不可用 |
| **优先级** | 高（P1）——需求 3.1.1 明确，修复成本低，属优惠券可用性判断 |
| **可复现性** | 必现（确定性，除跨午夜运行的极小概率外） |

- 优惠券：`ExpireDate = 今天`、`Threshold = 100.00`、`Amount = 10.00`、`IsUsed = false`。
- 订单金额：`100.00`。

## 复现步骤

1. 创建 `CouponService` 实例。
2. 构造优惠券，令 `ExpireDate = DateOnly.FromDateTime(DateTime.Now)`（截止日为今天）。
3. 设置 `Threshold = 100.00`、`Amount = 10.00`、`IsUsed = false`。
4. 调用 `IsUsable(coupon, 100.00m)`。
5. 观察返回值。

## 预期结果

返回 **`true`**（可用）。

计算过程：

- 条件 1（未过期）：今天 = 截止日，今天不晚于截止日，满足；
- 条件 2（达到门槛）：`100.00 ≥ 100.00`，满足；
- 条件 3（未使用）：`IsUsed = false`，满足；
- 三个条件同时满足 → 可用。

## 实际结果

返回 **`false`**（不可用）。

## 需求依据

- **需求 3.1.1（直接违反）**：未过期——今天不晚于有效期截止日（**截止日当天仍可用**）。
- **需求 3.1**：三个条件（未过期、达到门槛、未被使用）同时满足时可用，任一条件不满足即不可用。

## 测试证据

- 实际输出：

```text

Expected: True
Actual:   False
```

- 结果：失败。

## 影响范围

1. 当前 `CouponService` 尚未接入网页或 API，影响范围限于服务层调用方；一旦接入，所有在截止日当天使用优惠券的请求都会被判定为不可用。
2. 该判断同时影响 `Apply`：截止日当天即使满足门槛且未使用，也不会扣减面额（见缺陷报告 4）。
3. 截止日为昨天、明天，以及金额不足、已使用等场景行为正确，问题仅限“今天 == 截止日”这一边界。

## 缺陷位置（供定位）

`csharp/src/CampusShop/CouponService.cs:14`

## 建议（不含代码）

按需求 3.1.1 将截止日当天视为未过期，仅在“今天晚于截止日”时判定过期；保留该边界用例作为回归测试。

## 备注

- 期望值取自需求文档，而非当前实现结果。
- 测试使用“截止日相对今天的天数”表达日期，避免写死绝对日期；跨午夜运行时 `offset = 0` 的用例理论上存在极小概率波动。

| **缺陷类型** | 功能缺陷 / 数据一致性（库存回滚缺失） |
| **严重程度** | 高（Critical）——每一次支付失败都会永久扣减库存，库存数据持续偏差 |
| **优先级** | 高（P1）——需求 4.3 明确，且 `IInventoryRepository` 已提供 `Restore`，修复成本低 |
| **可复现性** | 必现（确定性） |
| **发现阶段** | 单元测试 |

## 前置条件

- .NET 10 SDK 环境，测试项目已引用 `CampusShop` 与 `CampusShop.Web`。
- 库存仓储替身中商品 `p1` 初始库存 = 10。
- 支付网关为 `FakePaymentGateway`（金额 > 5000 判定失败）。
- 通知发送正常。

## 复现步骤

1. 构造 `OrderService`，库存 10、支付网关为 `FakePaymentGateway`、通知发送为记录型替身。
2. 调用 `PlaceOrder(new Order("alice", "p1", 1, 5000.01m))`。
3. 读取返回结果，并查询 `p1` 的当前库存。

## 预期结果

- 返回 `OrderStatus.PaymentFailed`，提示“支付失败”。
- **最终库存 = 10**。

计算过程：

- 需求 4.1：库存 `10 ≥ 1`，检查通过；
- 需求 4.2：扣减库存，`10 − 1 = 9`；
- 需求 4.8：`5000.01 > 5000`，支付失败；
- 需求 4.3：失败后恢复库存，`9 + 1 = 10`，并返回“支付失败”。

## 实际结果

- 状态 `PaymentFailed`、提示“支付失败”均正确；
- **最终库存 = 9**，支付失败时未恢复库存。

## 需求依据

- **需求 4.3（直接违反）**：调用支付：失败 → 恢复库存，返回“支付失败”。
- **需求 4.2**：扣减库存在支付之前执行，因此失败路径必须回滚。
- **需求 4.1**：库存数据应与实际可售数量一致，否则后续下单会被误判为“库存不足”。

## 测试证据

- 测试用例：`OrderServiceTests.PlaceOrder_GivenOrderAndStock_ReturnsExpectedResult(quantity: 1, initialStock: 10, total: 5000.01, notificationThrows: False, expectedStatus: PaymentFailed, expectedMessage: "支付失败", expectedFinalStock: 10, expectPaymentCalled: True, expectNotificationSent: False)`
- 实际输出：

```text
Assert.Equal() Failure: Values differ
Expected: 10
Actual:   9
```

- 结果：失败。

## 影响范围

1. 任何支付失败的订单都会永久少掉对应数量的库存，误差随失败次数累积。
2. 需求 4.8 规定超过 5000 元的订单必定支付失败，这类订单 100% 触发缺陷。
3. 库存被错误扣减后，后续正常下单可能被误判为“库存不足”，用户看到虚假的缺货提示。
4. 当前 `OrderService` 尚未接入网页与 API 的下单链路（`POST /api/orders` 走的是 `OrderService`，需确认调用路径 【待确认】）；一旦启用，影响即扩散到线上订单流程。

## 缺陷位置（供定位）

- 表现位置：`csharp/src/CampusShop/OrderService.cs:26-27`（`Charge` 返回 false 时直接 `return`，未调用 `Restore`）。
- 库存已被扣减：`csharp/src/CampusShop/OrderService.cs:24`。
- 可用但未使用的恢复接口：`csharp/src/CampusShop/Dependencies.cs:14`；正确示范见 `csharp/src/CampusShop.Web/CheckoutService.cs:36`。

## 建议（不含代码）

支付失败分支在返回前按扣减时的相同商品与数量调用 `Restore`，再返回“支付失败”；保留该用例作为回归测试。

# 缺陷报告 6

| 字段 | 内容 |
|---|---|
| **缺陷编号** | BUG-CS-ORDER-006 |
| **缺陷标题** | 多件订单支付失败后库存未恢复：一次失败永久少 3 件库存 |
| **发现日期** | 2026-10-22 |
| **报告人** | 测试（待署名） |
| **项目 / 版本** | CampusShop C# 版 / main 分支 @ 04c5c31 |
| **所属模块** | `CampusShop.OrderService.PlaceOrder`（支付失败分支，多数量场景） |
| **缺陷类型** | 功能缺陷 / 数据一致性（库存回滚缺失） |
| **严重程度** | 高（Critical）——回滚缺失的量与购买数量成正比，多件订单损失更大 |
| **优先级** | 高（P1）——需求 4.3 明确 |
| **可复现性** | 必现（确定性） |
| **发现阶段** | 单元测试 |
| **状态** | 新建 |

## 前置条件

- .NET 10 SDK 环境，测试项目已引用 `CampusShop` 与 `CampusShop.Web`。
- 库存仓储替身中商品 `p1` 初始库存 = 5。
- 支付网关为 `FakePaymentGateway`。
- 通知发送正常。

## 复现步骤

1. 构造 `OrderService`，库存 5、支付网关为 `FakePaymentGateway`、通知发送为记录型替身。
2. 调用 `PlaceOrder(new Order("alice", "p1", 3, 6000.00m))`。
3. 读取返回结果，并查询 `p1` 的当前库存。

## 预期结果

- 返回 `OrderStatus.PaymentFailed`，提示“支付失败”。
- **最终库存 = 5**。

计算过程：

- 需求 4.1：库存 `5 ≥ 3`，检查通过；
- 需求 4.2：扣减库存，`5 − 3 = 2`；
- 需求 4.8：`6000.00 > 5000`，支付失败；
- 需求 4.3：恢复库存，`2 + 3 = 5`，并返回“支付失败”。

## 实际结果

- 状态 `PaymentFailed`、提示“支付失败”均正确；
- **最终库存 = 2**，未恢复 3 件库存。

## 需求依据

- **需求 4.3（直接违反）**：调用支付：失败 → 恢复库存，返回“支付失败”。
- **需求 4.2**：扣减发生在支付之前，失败时必须回滚相同数量。

## 测试证据

- 测试用例：`OrderServiceTests.PlaceOrder_GivenOrderAndStock_ReturnsExpectedResult(quantity: 3, initialStock: 5, total: 6000.00, notificationThrows: False, expectedStatus: PaymentFailed, expectedMessage: "支付失败", expectedFinalStock: 5, expectPaymentCalled: True, expectNotificationSent: False)`
- 实际输出：

```text
Assert.Equal() Failure: Values differ
Expected: 5
Actual:   2
```

- 结果：失败。

## 影响范围

1. 库存损失量等于订单数量，购买数量越大，数据偏差越大；`quantity = 99` 时一次失败即少 99 件。
2. 与缺陷报告 5 同源，但本条用“库存恰好接近耗尽”的数值（5 件中扣 3 件）证明偏差不是 1 件的偶然误差，而是整笔数量未回滚。
3. 库存台账与真实可售量持续背离，影响后续订单的库存判断。

## 缺陷位置（供定位）

- 表现位置：`csharp/src/CampusShop/OrderService.cs:26-27`。
- 扣减位置：`csharp/src/CampusShop/OrderService.cs:24`。

## 建议（不含代码）

同缺陷报告 5：支付失败时按扣减的商品与数量恢复库存。修复后本条用例可作为“回滚数量正确”的回归依据。

# 缺陷报告 7

| 字段 | 内容 |
|---|---|
| **缺陷编号** | BUG-CS-ORDER-007 |
| **缺陷标题** | 支付失败与通知异常同时出现时库存仍未恢复，回滚缺失与通知链路无关 |
| **发现日期** | 2026-10-22 |
| **报告人** | 测试（待署名） |
| **项目 / 版本** | CampusShop C# 版 / main 分支 @ 04c5c31 |
| **所属模块** | `CampusShop.OrderService.PlaceOrder`（支付失败分支，通知异常配置） |
| **缺陷类型** | 功能缺陷 / 数据一致性（库存回滚缺失） |
| **严重程度** | 高（Critical）——与报告 5 同一根因，在异常组合下依然稳定复现 |
| **优先级** | 高（P1）——需求 4.3 明确 |
| **可复现性** | 必现（确定性） |
| **发现阶段** | 单元测试 |
| **状态** | 新建 |

## 前置条件

- .NET 10 SDK 环境，测试项目已引用 `CampusShop` 与 `CampusShop.Web`。
- 库存仓储替身中商品 `p1` 初始库存 = 10。
- 支付网关为 `FakePaymentGateway`。
- 通知发送替身配置为**发送时抛异常**。

## 复现步骤

1. 构造 `OrderService`，库存 10、支付网关为 `FakePaymentGateway`、通知替身设置 `throwOnSend = true`。
2. 调用 `PlaceOrder(new Order("alice", "p1", 1, 6000.00m))`。
3. 读取返回结果，查询 `p1` 当前库存，并检查通知是否被发送。

## 预期结果

- 返回 `OrderStatus.PaymentFailed`，提示“支付失败”。
- **最终库存 = 10**。
- 通知不发送。

计算过程：

- 需求 4.1：库存 `10 ≥ 1`，检查通过；
- 需求 4.2：扣减库存，`10 − 1 = 9`；
- 需求 4.8：`6000.00 > 5000`，支付失败；
- 需求 4.3：恢复库存，`9 + 1 = 10`，返回“支付失败”；
- 需求 4.4：通知只在支付成功后发送，本路径不发送，因此配置的异常不会被触发。

## 实际结果

- 状态 `PaymentFailed`、提示“支付失败”正确；
- 通知未发送（符合需求 4.4）；
- **最终库存 = 9**，未恢复库存。

## 需求依据

- **需求 4.3（直接违反）**：调用支付：失败 → 恢复库存，返回“支付失败”。
- **需求 4.4**：支付成功后才发送通知；支付失败路径不涉及通知，因此本条排除了“通知异常导致库存未恢复”的可能，问题纯粹出在支付失败分支。

## 测试证据

- 测试用例：`OrderServiceTests.PlaceOrder_GivenOrderAndStock_ReturnsExpectedResult(quantity: 1, initialStock: 10, total: 6000.00, notificationThrows: True, expectedStatus: PaymentFailed, expectedMessage: "支付失败", expectedFinalStock: 10, expectPaymentCalled: True, expectNotificationSent: False)`
- 实际输出：

```text
Assert.Equal() Failure: Values differ
Expected: 10
Actual:   9
```

- 结果：失败。

## 影响范围

1. 与缺陷报告 5 相同的库存回滚缺失，本条证明它与通知链路是否异常无关。
2. 该组合场景下若实现依赖“异常被捕获后统一清理”的写法，也可能遗漏回滚；目前 `OrderService` 中并未出现任何清理逻辑。
3. 库存偏差会持续累积，导致后续订单误报“库存不足”。

- 表现位置：`csharp/src/CampusShop/OrderService.cs:26-27`。
- 扣减位置：`csharp/src/CampusShop/OrderService.cs:24`。

## 建议（不含代码）

同缺陷报告 5：支付失败分支在返回前恢复库存。修复后本条可作为“异常配置不影响回滚”的回归依据。
